# ТЕХНИЧЕСКОЕ ЗАДАНИЕ (ТЗ)

## Разработка CLI-приложения (Система контроля доступа и безопасности)

---

## 1. Общее описание проекта

Программа представляет собой консольное (CLI) приложение на платформе **.NET 8.0+ (C#)**, выполняющее роль системы управления физической безопасностью, контролем доступа, бронированием и обслуживанием помещений.

Проект разрабатывается с соблюдением принципов функционального программирования (**Functional Core / Imperative Shell**), включает взаимосвязанные доменные модели (сотрудники, карты доступа, помещения, бронирования, инциденты, записи аудита), сквозные бизнес-сценарии (Workflow), аналитическую отчётность на базе LINQ и сохранение состояния в локальном файловом хранилище.

Приложение функционирует в интерактивном режиме с непрерывным циклом обработки ввода (REPL pattern):
$$\text{Start} \longrightarrow \text{User Input} \longrightarrow \text{Response} \longrightarrow \text{Waiting for Input}$$

## 2. Архитектурные требования и стек технологий

### 2.1. Технологический стек

* **Язык и платформа:** C# 12+, .NET 8.0+
* **Формат данных:** JSON (использование `System.Text.Json`) для хранения данных и экспорта отчётов
* **Стиль программирования:** Функциональный подход (Functional Core / Imperative Shell)
* **Тестирование:** xUnit / NUnit (детерминированный прогон тестов с отчётом Pass/Fail)

### 2.2. Требования к функциональному стилю

1. **Разделение чистого ядра и побочных эффектов (Functional Core / Imperative Shell):**
   * Вся бизнес-логика, валидация, вычисления и построение отчётов реализуются в виде чистых функций без обращения к `Console`, файловой системе или изменяемому глобальному состоянию.
   * Весь ввод-вывод изолирован на границах приложения (в CLI-оболочке и слое персистентности).
2. **Неизменяемость (Immutability):**
   * Все доменные модели и состояния описываются с помощью неизменяемых типов (`record`, `readonly record struct`, неизменяемые коллекции `IReadOnlyList<T>` / `ImmutableList<T>`).
   * Запрещена модификация коллекций, переданных вызывающим кодом (все трансформации возвращают новые коллекции).
3. **Сопоставление с образцом (Pattern Matching):**
   * Использование `switch`-выражений, сопоставления по свойствам и типам для принятия ключевых доменных решений (проверка режимов работы здания, уровней допуска и переходов статусов заявок).
4. **Обработка ошибок без Exception (Functional Error Handling):**
   * Использование типа `Result<T>` (или `Result<T, TError>`) минимум для **трёх различных доменных ошибок** (например: `CardNotFound`, `EmployeeInactive`, `InsufficientClearance`, `RoomOverlap`, `TicketAlreadyResolved`).
   * Использование шаблона `Maybe<T>` для явного представления отсутствующих результатов поиска вместо `null`.
   * Обязательное применение комбинаторов **`Map`** и **`Bind`** в реальных сценариях так, чтобы ошибка на раннем этапе автоматически пропускала последующие зависимые шаги.
   * Перехват операционных исключений (`IOException`, `JsonException`, `UnauthorizedAccessException`) строго на границах ввода-вывода с преобразованием их в понятные ошибки `Result`.
5. **Безопасная последовательность операций (Safe Operation Sequence):**
   * Зависимости между шагами операций выражаются явно через систему типов, фабрики или валидированные обёртки состояний (например: `UnverifiedScan` $\rightarrow$ `VerifiedCard` $\rightarrow$ `AccessDecision`, а также разделение `OpenTicket` и `ResolvedTicket`).
   * Архитектура должна предотвращать или отвергать вызов операций в неверном порядке (например, попытку повторного закрытия уже решённого инцидента или выдачу доступа без проверки активности карты) без необходимости помнить скрытый порядок вызовов.
6. **Конвейерная обработка (Pipeline) и функции высшего порядка (HOF):**
   * Реализация рабочего конвейера (Pipeline) минимум из **трёх именованных этапов трансформации**, где выход одного этапа передаётся на вход следующему, а ввод-вывод вынесен за пределы конвейера.
   * Использование функций высшего порядка, принимающих `Func<...>` или пользовательские делегаты, которые **реально изменяют бизнес-правила** (например, динамическая политика допуска в зависимости от режима работы здания: штатный режим, ночной режим, режим блокировки).
   * Применение каррирования (Currying) и частичного применения (Partial Application) для конфигурации правил доступа и предикатов фильтрации.
7. **Запросы, расширения и ленивые вычисления (LINQ, Extensions & Lazy Processing):**
   * Реализация минимум **двух пользовательских методов расширения (Custom Extension Methods)**, активно используемых в бизнес-логике или конвейерах.
   * Реализация **двух аналитических LINQ-отчётов**, совокупно включающих: фильтрацию (`Where`), проекцию (`Select`), сортировку с вторичным критерием при равенстве (`OrderBy` + `ThenBy`), группировку (`GroupBy`) и агрегацию (`Count`, `Sum`, `Average`).
   * Реализация потокового сценария на базе `IEnumerable<T>` с использованием `yield return`, демонстрацией отложенного выполнения (deferred execution) и осознанной материализацией (`.ToList()` / `.ToArray()`) на границе, где требуется переиспользуемый снимок данных.

## 3. Реестр Workflow (Командный интерфейс)

Система поддерживает 6 согласованных модулей (Workflow), работающих с единой доменной моделью, вызываемых через текстовые команды в консоли:

```text
sec-cli> <command-name> [arguments...]
```

### 3.1. Workflow 1: `scan-card` (Контроль доступа)

* **Команда:** `scan-card <card_id> <room_id>`
* **Назначение:** Эмуляция прикладывания карты к считывателю у двери/турникета с проверкой прав доступа и записью в журнал аудита.
* **Логика (Pipeline из 4 этапов через `Bind` и `Map`):**
  1. **Этап 1 (`LookupEntities`):** Поиск карты по `card_id` и помещения по `room_id` с использованием `Maybe<T>` и преобразованием в `Result` (ошибка `EntityNotFound`).
  2. **Этап 2 (`VerifyCardAndEmployee`):** Проверка активности карты и статуса привязанного сотрудника с переводом в валидированное состояние `VerifiedCard` (ошибка `InactiveAccountOrCard`).
  3. **Этап 3 (`EvaluateAccessPolicy`):** Проверка прав прохода в `room_id` через каррированную функцию высшего порядка с учётом текущего режима здания из конфигурации:
     $$\text{validateAccess} : \text{BuildingMode} \rightarrow \text{TimeSpan} \rightarrow \text{RoomLevel} \rightarrow \text{VerifiedCard} \rightarrow \text{Result}<\text{AccessDecision}, \text{SecurityError}>$$
  4. **Этап 4 (`AppendAuditLog`):** Формирование новой записи события (проход разрешён / отказ с причиной) и сохранение обновлённого `audit.json` на границе ввода-вывода.

### 3.2. Workflow 2: `support-ticket` (Управление инцидентами)

* **Команды:**
  * `support-ticket list [--status <open|closed>]`
  * `support-ticket create <employee_id> <description>`
  * `support-ticket resolve <ticket_id>`
* **Назначение:** Учёт заявок на ремонт замков, неисправности считывателей и инциденты безопасности.
* **Логика:**
  * Валидация существования сотрудника при создании заявки.
  * Типобезопасный переход состояния заявки (`OpenTicket` $\rightarrow$ `ResolvedTicket`): попытка повторно закрыть уже закрытую заявку отклоняется доменной ошибкой `TicketAlreadyResolved`.

### 3.3. Workflow 3: `reservation` (Бронирование помещений)

* **Команды:**
  * `reservation book <room_id> <employee_id> <start_time> <end_time>`
  * `reservation cancel <reservation_id>`
  * `reservation list <room_id>`
* **Назначение:** Бронирование переговорных комнат и закрытых зон с проверкой допуска и конфликтов расписания.
* **Логика:**
  * Проверка корректности временного интервала ($\text{start\_time} < \text{end\_time}$) и уровня допуска сотрудника к помещению.
  * Проверка пересечений интервалов времени с существующими активными бронями через предикаты высшего порядка (ошибка `TimeSlotConflict`).

### 3.4. Workflow 4: `audit-log` (Ленивый поток и анализ журнала событий)

* **Команды:**
  * `audit-log stream [--employee <id>] [--room <id>] [--denied-only]`
  * `audit-log anomalies [--threshold <count>]`
* **Назначение:** Потоковая фильтрация журнала событий безопасности и выявление подозрительной активности (многократных отказов доступа).
* **Логика:**
  * Использование генератора `IEnumerable<AuditEntry>` с `yield return` для пошаговой ленивой фильтрации записей без загрузки промежуточных выборок в память.
  * Осознанная материализация (`.ToList()`) на границе формирования итогового снимка для вывода в консоль или выявления аномалий.

### 3.5. Workflow 5: `report` (Аналитические LINQ-отчёты и экспорт)

* **Команды:**
  * `report access-summary [--export <file_path>]`
  * `report room-utilization [--export <file_path>]`
* **Назначение:** Формирование двух сводных аналитических отчётов на базе LINQ с возможностью экспорта результатов в JSON-файл.
* **Логика:**
  1. **Отчёт 1 (`access-summary` — Статистика проходов и нарушений по сотрудникам):**
     * Фильтрация событий (`Where`), группировка по сотрудникам/отделам (`GroupBy`), агрегация общего числа попыток и количества отказов (`Count`), сортировка по убыванию числа нарушений с разрешением ничьих по имени сотрудника (`OrderByDescending` $\rightarrow$ `ThenBy`), проекция в DTO отчёта (`Select`).
  2. **Отчёт 2 (`room-utilization` — Загруженность помещений):**
     * Фильтрация подтверждённых бронирований (`Where`), группировка по помещениям (`GroupBy`), агрегация суммарной длительности брони и количества сессий (`Sum`, `Count`), сортировка по убыванию суммарных часов с разрешением ничьих по идентификатору помещения (`OrderByDescending` $\rightarrow$ `ThenBy`), проекция (`Select`).
  * При указании флага `--export <file_path>` результат отчёта сериализуется и сохраняется в файл через слой персистентности.

### 3.6. Workflow 6: `config` (Управление конфигурацией и политиками доступа)

* **Команды:**
  * `config show`
  * `config set-mode <normal|night|lockdown>`
  * `config set-hours <open_time> <close_time>`
* **Назначение:** Чтение и динамическое изменение системных параметров (режим безопасности здания, рабочие часы, минимальный уровень допуска при блокировке).
* **Логика:**
  * Изменение `config.json` через чистую функцию обновления конфигурации.
  * Выбранный режим работы здания определяет делегат политики доступа (`Func<Employee, Room, TimeSpan, Result<bool, SecurityError>>`), передаваемый в конвейер `scan-card`.

## 4. Спецификация JSON-хранилища и персистентности

Данные хранятся в локальной файловой системе в формате JSON. Чтение, запись и экспорт отчётов изолированы от чистых функций доменной логики.

### 4.1. Состав файлов данных

* `employees.json` — реестр сотрудников, их отделов, уровней допуска и статусов активности.
* `cards.json` — реестр идентификационных карт и их привязка к сотрудникам.
* `rooms.json` — реестр помещений, их типов и требуемого уровня допуска.
* `tickets.json` — список заявок техподдержки и инцидентов.
* `reservations.json` — журнал бронирования помещений.
* `audit.json` — журнал событий контроля доступа (попытки прохода и отказы).
* `config.json` — настройки приложения (режим работы здания, рабочие часы).

### 4.2. Требования к загрузке, валидации и примерам данных

* **Настраиваемые/относительные пути:** Путь к директории данных должен задаваться через конфигурацию или аргумент запуска (по умолчанию относительный каталог `./data`).
* **Примеры данных (Sample Data):** В состав проекта включается набор валидных демонстрационных JSON-файлов для быстрого запуска и проверки всех сценариев.
* **Валидация при загрузке:** При чтении JSON выполняется структурная и доменная проверка загруженных записей (корректность ID, диапазонов времени, уровней допуска).
* **Обработка сбоев файлов:** Отсутствующие файлы (`FileNotFoundException`) или повреждённый синтаксис JSON (`JsonException`) должны перехватываться на границе ввода-вывода и возвращаться в виде понятного описания ошибки (`Result.Fail`), не приводя к аварийному завершению приложения.

## 5. Пример реализации базовых функциональных типов (C#)

### 5.1. Тип Result

```csharp
public abstract record Result<T>
{
    private protected Result() { }
    public sealed record Ok(T Value) : Result<T>;
    public sealed record Fail(string Error) : Result<T>;
}
```

### 5.2. Тип Maybe

```csharp
public abstract record Maybe<T>
{
    private protected Maybe() { }
    public sealed record Some(T Value) : Maybe<T>;
    public sealed record None : Maybe<T>;
}
```

### 5.3. Функции Map и Bind

```csharp
public static Result<U> Map<T, U>(this Result<T> r, Func<T, U> f) => r switch 
{
    Result<T>.Ok(var x) => new Result<U>.Ok(f(x)),
    Result<T>.Fail(var e) => new Result<U>.Fail(e),
    _ => throw new ArgumentException("Unknown case")
};

public static Result<U> Bind<T, U>(this Result<T> r, Func<T, Result<U>> f) => r switch
{
    Result<T>.Ok(var x) => f(x),
    Result<T>.Fail(var e) => new Result<U>.Fail(e),
    _ => throw new ArgumentException("Unknown case")
};
```

### 5.4. Безопасная последовательность операций (State Types)

```csharp
// Запрет выдачи доступа без предварительной валидации карты и сотрудника
public sealed record UnverifiedScan(string CardId, string RoomId, TimeSpan Timestamp);
public sealed record VerifiedCard(Card Card, Employee Owner);
public sealed record AccessDecision(VerifiedCard Subject, Room TargetRoom, bool Granted, string Reason);
```

### 5.5. Каррированная проверка доступа и Pattern Matching

```csharp
public static class AccessRules
{
    public static Func<BuildingMode, Func<TimeSpan, Func<Room, Func<VerifiedCard, Result<AccessDecision>>>>> CheckAccess =>
        mode => currentTime => room => verified =>
        {
            var employee = verified.Owner;

            return (mode, employee.ClearanceLevel >= room.RequiredLevel) switch
            {
                (BuildingMode.Lockdown, _) when employee.ClearanceLevel < 5 =>
                    new Result<AccessDecision>.Fail("Здание в режиме блокировки: требуется максимальный уровень допуска"),
                (_, false) =>
                    new Result<AccessDecision>.Fail("Недостаточно прав доступа для данного помещения"),
                (BuildingMode.Night, true) when employee.ClearanceLevel < 3 =>
                    new Result<AccessDecision>.Fail("Доступ в ночное время ограничен"),
                _ =>
                    new Result<AccessDecision>.Ok(new AccessDecision(verified, room, true, "Доступ разрешён"))
            };
        };
}
```

## 6. Требования к автоматизированному тестированию (Automated Testing)

Разработка приложения должна сопровождаться написанием **минимум 12 автоматизированных тестов** (xUnit / NUnit + FluentAssertions) с детерминированным выполнением и итоговой сводкой Pass/Fail.

### 6.1. Модульное тестирование (Unit Tests — минимум 8 тестов)

* **Функциональные типы (`Result`, `Maybe`) и расширения:** Покрытие тестами `Map`, `Bind`, распространения ошибок (пропуск последующих этапов при `Fail`) и пользовательских методов расширения.
* **Чистые функции бизнес-логики и валидации:** Тестирование каррированной проверки доступа (`CheckAccess`), сопоставления с образцом для режимов здания, валидации пересечений интервалов бронирования (`reservation`) и ленивой фильтрации (`audit-log`).
* **Безопасная последовательность операций:** Проверка отклонения некорректных переходов состояний (например, повторное закрытие решённой заявки).
* **Покрытие граничных случаев:** Нормальные, граничные, невалидные, пустые и отсутствующие входные данные.

### 6.2. Интеграционное тестирование Workflow (Workflow Tests — минимум 2 теста)

* **Сквозные сценарии конвейера:** Пошаговая эмуляция полных команд (`scan-card`, `reservation book`, `report access-summary`) как для успешного выполнения, так и для ожидаемого бизнес-отказа с проверкой целостности итогового состояния.

### 6.3. Тестирование файлового хранилища (Persistence Tests — минимум 2 теста)

* **Отсутствующий файл (Missing File):** Проверка корректной обработки ситуации, когда целевой JSON-файл не существует, с возвратом ожидаемого `Result.Fail`.
* **Повреждённый контент (Malformed Content):** Проверка загрузки JSON-файла с синтаксической ошибкой или невалидными данными без необработанных исключений.
* *Примечание:* Тесты ввода-вывода должны использовать изолированные временные каталоги.

### 6.4. Свойства и инварианты (Property-Based Testing — Опционально)

* Использование библиотеки FsCheck для проверки инвариантов бизнес-логики (например, невозможность двойного бронирования помещения на пересекающийся интервал времени при любых случайных входных данных).
